# 法律文书起草与改写

改编自用户提供的 /legal-writing。保留完整交付、独立论证、原稿改写和来源核对方法，适配茶渡的茶商咨询与文稿工具。仅问法律结论时使用已有 legal 方法；查法规用 legal_lookup；合同风险审查与谈判修改使用 contract_review。本技能负责把事实和法律依据组织成用户所需的文书，也可起草业务说明等普通文稿。无需先生成法律子报告。

融合 Legal-Agent-Skills document-fill 的填写值溯源，LegalQuants CoQuill 的模板与变量识别、legal-translation 的术语和法律效果保留方法。来源与许可见技能目录 NOTICE.md。方法按需使用，不强制填写计划 JSON、额外访谈、渲染子 Agent 或逐项审批。

## 确定交付内容

复用用户已说明的目的、读者、代表方、相关主体、法域、行为日期和文书要求。读取用户提供的原稿、合同、附件、证据及格式要求，记录实际读取的版本和范围。只在决定文书立场、收件人、请求或程序的事实缺失时简短追问；其他缺项用明确的待填位置处理，继续完成能够起草的内容。不要读取学生档案、课程记录或 Claude 配置，不假定存在谈判手册、格式要求或私人文件。

按本次请求选择交付方式，无需依次执行所有方式：

- 起草：用户要求写、拟定或完成文书时，交付内容连贯的完整初稿；已有事实足够时，不用提纲、通用模板或教学点评替代正文。事实缺失处保留必要待填项，不能凭空写入当事人、金额、证据、履行经过或程序历史。
- 改写：按要求提供全文或指定部分，保持用户的立场、请求、材料中的事实与已经明确的条件。修正论证、术语、引用及交叉指引；涉及改变请求范围、让步或实质义务时，在稿外说明拟议变化，不能将其当成用户已接受的安排。
- 反馈：用户只要评价时，指出影响使用的主要问题，解释修改办法，必要时给短例句；不默认重写整篇。评价依据本次目的和已知要求，不套用假设的课程评分标准，也不建立长期学习档案。
- 研究：为文书确认规则、引用或法律立场时，查明直接相关的原文和版本，再将结果用于正文。用户只要求研究时直接交付发现与出处，不额外起草文书。

## 用事实与原文支持论证

区分用户陈述、材料记载、明确假设、对方主张和未知事实。对外文书中可用“据我方现有材料”“我方主张”等符合语境的表述，不能把单方陈述改为已经证明或对方认可的事实。未提供违约金、管辖或责任分工条款时保持未知；用户明确排除的抗辩不再作为起草障碍。

法律论证沿用 legal 的规则解释与事实对应方法：确定请求或义务、实际承担者、适用条件和法律效果，解释本案事实为何支持判断；处理会改变结果的例外、不利依据和合理反驳。证明责任、证据要求、法律选择与程序规则只在相关时分析，某一主体所在地不自动决定所有争点的适用法律。法律上可主张与材料能否证明分别说明。

用 list_documents、read_document、search_documents 取得可访问的业务材料；仅在需要补充任务信息时用 guide_business，已明确保存的笔记可用 recall_memory。已知中国法名称和条号用 lookup_chinese_law，未知规则用 search_legal_evidence，补读用 read_law，已有版本关系用 get_law_versions；必要时 web_search 定位官方来源。联网查询只使用公共法律问题，不发送私有合同或当事人信息。按需调用，已有结果复用，缺一项材料只限制相关判断。

法律数据先查内部库，缺相关原文、版本或材料再补查外部官方来源。模板中的姓名、金额、日期等个案事实只取自当前业务材料或用户明确确认，不用公共网页或模型常识填补。本业务材料不足的字段留待补充；计算值、推测、冲突与摘录分开，不能把推算写成原文记载。

法律主张须对应读到的原文、条款位置、实际法域与适用时间。搜索摘要保留线索身份，学术观点、商业解读及第三方条文接口标明来源性质；不虚构案例、条号、引文、页码、链接或检索结果。法院裁判的参考作用按其法域和实际地位说明，不能套用外国判例制度。无法核对的内容说明具体缺口，未查到不能推出规则不存在；没有依据的胜诉概率、利率、赔偿比例和程序期限不写成确定值。

## 按文书用途组织正文

起草茶叶交易合同时，直接用read_contract_template(template="tea_purchase"／"tea_export"／"export_agency"／"tea_distribution")读取境内采购、跨境销售、委托出口或经销的对应正文；无需先搜索业务库。也可用load_skill(name="draft", resource="assets/contracts/tea-purchase.md")按资源名读取。交易关系或文件格式仍需确认时，才读取[选择说明](references/contracts.md)。官方原件、日期及改编范围见[模板来源](references/contract-sources.md)；用户要求官方模板或需要核对原文时读取assets/sources的文本。模板用于约定交易，不能作为证明手续法定必需的依据。用户提供原合同或指定格式时优先保留其要求。

需要合同文件时，已有模板可用create_document_file的template与replacements按原文字面填写已知事实，其余条款由程序保留，不用模型重传全文；此方式默认contract版式。需要实质重新起草时传完整content及layout="contract"。来源、待确认问题和起草解释放在稿外，不能把技能说明或文件调用代码写进合同。用户只要正文时直接交付正文。draft_document仅保存工作台Markdown，不能代替可下载附件。

催款函、履约通知和法律往来函写清发函主体、背景、请求及对方可采取的行动。付款期限、解除条件及后果区分已有约定、法定要求与本次建议；没有支持时不声称已满足解除、送达或起诉条件。文书中的“我方”“委托人”等身份须有事实基础，不冒充已经接受委托的律师或机构。

法律意见与合规报告围绕用户要作的决定组织：说明所用事实、适用范围、判断理由和可执行事项，相关时写明责任方与所需材料。争议或诉讼文书区分事实陈述、证据和请求，按已知的程序阶段及受理要求拟稿；未知的案号、法院、期限或送达情况留待核对。合同与条款使用一致的主体、定义、付款和履行条件，保持风险分工、违约责任、解除及争议条款相互协调。研究文章按用户要求组织论点、依据和反论证，学术格式仅在任务需要时采用。

结构随文书类型和用户要求变化，不将每份文书写成“结论、为什么、法律依据”问答。面向茶商的解释用日常语言；合同或诉讼文书使用必要的专业表述。用户指定引用规范时遵循，精确到条、款、页等已核对的位置；平台答复中的来源编号紧随相关判断，详细出处沿用现有引用入口，不编造脚注。

## 缺项、自检与交付

用户要求填写模板或表单时，按需用 load_skill(name="draft", resource="references/template-fill.md") 读取字段来源、冲突与文件填写方法；需要翻译或双语文书时读取 references/translation.md。未要求翻译时保持用户语言。仅加载本次需要的参考文件，不运行上游渲染器，不读取学生配置或建立访谈档案。

起草中需要区分时，可在稿外使用“待核对依据”“待补充事实”“本稿假设”“待填写”说明，指出缺什么、影响哪项判断。正文仅保留无法替代的待填位置，避免遍布内部标签。假设只用于本次拟稿，不能写入业务卡或长期事实记录。存在会影响使用的缺项时称为初稿，说明哪些内容补齐前不能据此签署或提交，不以行文完整推定可正式使用。

交付前在本次生成中核对主体、日期、金额、定义、请求、条号、交叉引用和已知来源，检查法律条件、例外及用户各项要求有无遗漏。该检查由同一主 Agent 完成，不增加固定审核模型、第二份报告或常规润色调用。无法核对的内容保留限制，不通过自动改写掩盖事实或依据缺口。

起草或改写请求先给完整正文，必要的假设、待核对事项和实质修改说明简短放在稿后；只要清洁正文时将说明与文书分开。反馈请求交付有理由的意见。不要将内部工具记录、审核状态、计划或反复保留说明写入文书，也不在完成后追加通用邀请。

用户要求在工作台创建或保存文稿时，将完整 Markdown 正文交给 draft_document，使用当前节点的真实 task_id；不猜编号，不把保存能力缺失当成无法在对话中交付正文。正文超过工具已发布的长度限制时保留对话交付并说明保存限制，不能截断内容后声称全文已保存。遵循现有版本与事务规则，pending_commit 只表示待提交，保存成功由程序确认。单纯点评或提供咨询不另存文稿，不覆盖用户原稿，不自行发送、签署或提交文书。
