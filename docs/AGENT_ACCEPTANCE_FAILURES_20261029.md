# 2026-10-29 业务验收失败原因调查

本次调查核对当前Nemotron六题的模型轮次、工具收据、任务状态和法律分析记录，并回溯前一轮Gemini的专业结果。结论分为已复现的软件缺陷、已确认的上游错误，以及尚不能确定的供应商内部原因。调查未修改应用运行逻辑或线上模型配置。

模型摘要事件表明D01超时轮次在整题26.978秒已开始返回内容，直到90.067秒仍有事件；D04第二轮在8.795秒开始返回内容。两次超时均发生于已建立连接的模型轮次。该证据不能确定未返回部分究竟由模型生成、供应商排队还是网关内部处理耗时造成。

## 工具发现与任务状态缺陷

[`agent_tools.py`的discover](../backend/app/contexts/conversations/application/agent_tools.py)以英文词和中文双字词匹配工具名称、说明和能力字段。当前实现缺少将业务请求映射到专业能力的语义处理。以下结果用原始查询在本地确定性复现，无需外部模型：

| 输入tool_search的query | 实际激活工具 |
| --- | --- |
| 对外贸易经营者备案 个体工商户 | guide_business |
| 商务部 外贸备案管理办法 | 空 |
| 进出口货物收发货人备案 对外贸易经营者备案 区别 | guide_business |
| 传统黑茶展示证 六堡茶 进口 印尼 | update_task_brief |
| search_legal_evidence | search_legal_evidence |
| analyze_legal | analyze_legal |

模型把工具目录查询当作法规查询，而目录返回的是函数参数定义。D03三次调用没有取得任何法律原文，D05一次调用也没有取得任何法规或网页。

[`agent_loop.py`](../backend/app/contexts/conversations/application/agent_loop.py)首轮仅设置`tool_choice=required`，含义为必须调用某项已提供工具，未限定任务说明必须被记录。D03、D04、D05均选择了工具发现，Task Brief保持`general`、目标为空、法域为空。后续要求调用法律工具的调度条件依赖已记录的任务类型或能力，因而没有触发。

同一文件的`made_progress`将工具发现计作进展，即使结果为空或只重复加载相同能力也会通过该判断。当前“无新进展则停止”的逻辑未覆盖这种情况。

## 单轮预算与最终交付入口缺陷

整题预算为90秒，停止继续调度的50秒判断在模型轮次开始前执行。`MODEL_TURN`自身的超时声明为180秒，实际请求使用整题剩余时间。一次在第7秒开始的调用可持续到第90秒，无法在第50秒重新进入调度判断。专业分析的60秒截止时间只有在调用法律工具后才生效，不能约束此前的模型规划。

D01的最后一轮耗时64.023秒，D04最后一轮耗时82.481秒，两者均没有为最终整理留下时间。这是调度预算分配问题，不能将“50秒后停止补查”解释为当前已有可靠的单轮截止机制。

最终整理只在`final_only`为真时使用`composition_messages`。普通规划轮次若返回非工具正文，代码立即调用`finish`，无需进入最终整理。D03第二轮开始时整题约28秒，D05第二轮开始时约3秒，均未达到50秒条件；模型随后直接返回正文，因此未使用最终整理的专业材料限制。

D03的中断说明被记录为`delivery=answered`。D05在没有实际法律或网页查询收据的情况下输出了法律要求、来源数量和无法回查的引用编号。当前完成状态以返回正文为判断依据，没有区分传输结束、正文生成与用户任务完成。

## 上游502的确定范围

B01和D02原始日志确认上游HTTP 502；当时没有返回正文或工具调用。原始记录没有保存供应商错误正文和上游请求标识，因此无法从本地材料确定其内部故障原因。

本次进行了五个有界诊断请求，均使用隔离脚本；正式工作台继续保持Nemotron-3.5 / high：

| 诊断 | 结果 | 耗时 |
| --- | --- | ---: |
| 小型工具调用，high | HTTP 200，返回正确工具名 | 14.610秒 |
| 将随机凭据放入工具结果并续答，high | HTTP 200，答复包含仅在工具结果提供的随机值 | 1.320秒 |
| 实际首轮结构重放，high，约16.2KB | HTTP 200，返回任务说明工具调用 | 30.035秒 |
| 同一首轮输入，诊断进程内low对照 | HTTP 200，返回工具发现调用 | 9.145秒 |
| 商业题首轮结构，high，约16.1KB | HTTP 200，返回任务说明工具调用 | 15.228秒 |

这些结果证明凭据、文本请求、工具调用及工具结果回传在对应请求中可用，实际规模的首轮结构也能被接受。没有证据支持“密钥始终无效”或“该接口固定不支持工具调用”的判断。先前502与本次同类请求成功共同表明请求结果存在波动。供应商内部成因仍未确定，不能将其直接写成上下文过长、额度耗尽或服务器过载。

high与low各一次的对照包含模型选择、缓存和服务时延差异，只用作诊断样本。它不构成稳定性能或法律质量比较，也未改变工作台的high配置。

`agent_transport.py`对HTTP错误直接执行`raise_for_status`，而聊天流只对`AppError`保留具体错误。上游HTTP异常进入通用异常处理后，用户看到相同的“回复未能完成”文案。它使接口失败与模型超时难以从用户界面区分。[流式错误处理](../backend/app/shared/application/streaming.py)是错误分型丢失的位置。

## 前一轮法律质量问题的发生位置

回溯Gemini轮次发现，主体错误已经进入法律工具的结构化结果。此前将这些问题主要归于最终整合，定位不完整。

D04境内争点的专业结论已写“严禁贸易商代办生产资质”，并将生产企业和种植场统一写成甲茶厂。题目只明确甲茶厂生产茶叶，没有提供其也是种植主体的事实。该争点又将合同责任方写为甲茶厂，题目未给出对应合同分工。

D04印尼争点把“经当地零售商销售”作为“进口零售预包装食品”的已满足条件，并出现“严禁越权办理”的专业解释。登记名义、操作委托和包装事实在这一处已经发生混淆，最终答复继续沿用了这些判断。

D05专业结果把证件存在性的条件写为`not_met`，理由为现行制度不存在该名称凭证。已取得材料不足以穷尽所有可能规定；本次未查明的事实被转换成确定的否定判断。专业解释还自行补充了其他单证要求，后续整合延续并扩大了该内容。

现有结构保留了主体、条件和引用编号，但字段填充不能代替规则适用判断。上述问题分别发生在事实推断、登记与办理关系解释、检索未命中的法律效果推断，均可在专业结果进入最终答复之前定位。

## 验证覆盖与材料位置

现有受控测试能够验证协议、权限、参数和收据保存。部分旧场景的`scenario()`帮助器会自动插入精确工具名搜索，再交付预先安排的工具调用；这些测试未检验真实模型能否从业务提问发现正确能力。最终整理测试也未保证所有真实答复都会经过该入口。因此，受控测试通过与本批业务失败之间有明确的覆盖差异。

本次仅新增诊断脚本与调查记录。证据位于工作树`.dev/agent-runtime/failure-investigation/`：`provider-probes.json`保存脱敏请求统计，`discovery-reproduction.json`保存工具发现复现，`turn-timings.json`保存逐轮耗时及事件计数。诊断文件未记录密钥或完整模型思考。
