# 向量并发、检查点与续跑

向量任务按账号、原件版本、模型标识和实际输入校验。只有正文完整且具备一级检索资格的资料进入向量任务；生成向量不改变法规的审核、国家或有效期门禁。共享法律总库使用系统主体，用户上传资料继续按账号隔离。

## 并发参数

| 参数 | 默认 | 范围与作用 |
| --- | --- | --- |
| `TEA_PROCESS_WORKERS` | 2 | 1–128；同库解析与向量任务的总领取额度 |
| `TEA_EMBED_WORKERS` | 2 | 1–32；向量文档任务额度，不超过总领取额度 |

| `EMBEDDING_HTTP_WORKERS` | 2 | 1–64；同机同模型共享 HTTP 上限，API 与运行脚本必须配置相同值 |
| `EMBEDDING_ADMISSION_PATH` | 实例 `data/control/embedding-admission.sqlite3` | API 与后台共用的额度库，跟随 `TEA_DATA_DIR`；可以显式指定独立磁盘路径 |
| `EMBEDDING_REQUEST_CONCURRENCY` | 1 | 1 或 2；同文档一次处理中的请求并行数 |

`TEA_PARSE_WORKERS` independently bounds parser work per process and supports 1–128. Raise it only to feed a higher MinerU API concurrency stage; keep embedding request concurrency under its separate admission and provider limits.
| `EMBEDDING_BATCH_SIZE` | 64 | 1–64；每次请求的文本段数 |
| `EMBEDDING_HTTP_TIMEOUT_SECONDS` | 30 | 1–60 秒；HTTP 超时，整次调用另有 300 秒总边界 |
| `EMBEDDING_RETRY_AMBIGUOUS_TIMEOUTS` | true | 正式续跑脚本固定 false；响应不明时先留证，不自动重发 |
| `EMBEDDING_INPUT_CACHE` | false | 同账号、同模型、实际输入完全相等时复用已有向量 |

API 和正式运行脚本在同一台 Linux 主机上，通过同一路径、同一服务地址和模型摘要共享 SQLite 额度。实现依赖 Linux `/proc` 进程启动身份，不跨主机共享，也未验证 macOS 或 Windows。64 路配置为查询预留 4 个名额，后台最多 60 个；两类同时等待时，后台低于 16 个在途请求会优先补足，其他空位优先分配查询，同类按先到先服务。额度限制每个实际 HTTP 请求，不截短长文档，后台逐批继续。默认上限仍为 2；仅直接调用库函数且未配置共享路径时使用进程内队列。

提高并发应比较成功输入字符数、耗时、实际请求峰值和错误率。共用数据库的 OCR 租约也会占用总领取额度，配置 64 不代表后台同时发出 64 个请求。独立 API 和后台进程的本地 HTTP 回归已实测 60 个长文请求占用时，4 个查询进入预留名额，总峰值 64，68 个输入全部完成；该验证使用本地模拟服务，不代表外部供应商能持续承受相同负载。

额度库保存进程 PID、启动身份、请求类别和租约，不保存密钥、正文或向量。进程退出、PID 重用和超时租约会被回收；主动取消和正常完成释放名额。首次并发启动使用原子初始化；误指向业务数据库、其他协议 SQLite、符号链接或硬链接会拒绝使用。已占用额度时修改上限会拒绝，须先排空并重启所有使用该额度的进程。429 的冷却时间共享给前后台，查询等待也受既有总调用期限约束。

成套实例备份保留额度、统计和供应商冷却时间；`make instance-restore` 在新副本中释放旧机器的进程租约，不修改备份或原实例。不要直接复制额度库后让新旧机器同时使用。配置归集与迁移命令见 [实例管理](INSTANCE_MANAGEMENT.md)。

2026-10-19 的真实服务探测中，32 路、每请求 2 段的一个持续窗口达到实际峰值 32，最终排空窗口的 298 次请求全部成功；提高到目标 64 路、每请求 1 段后，实际峰值 59，最终 473 次请求中 464 次 HTTP 200、9 次 429，另保留一个响应处理被取消、结果未确认的输入记录。观察窗口的成功字符吞吐没有显示 64 路更快，因此当次续跑回到 32 路、16 个文档任务各并行 2 请求、每请求 2 段、60 秒超时。文本长度和窗口不同，这不是受控性能基准，也不保证后续不会限流。

后续服务端故障窗口累计 413 次请求中有 42 次 504、4 次 503 和 1 次读取超时；原重试路径产生 76 条重复输入发送记录，实际计费状态未知，旧审计保留。修复后的正式入口停止新增文档领取时也禁止尚未发出的内部重试，并在关闭模糊重试时隔离 408/5xx 及连接结果不明的请求。恢复先用 16 路 HTTP、8 个文档任务，363 秒窗口 146/146 请求成功；随后提高到 24 路 HTTP、12 个文档任务，每文档 2 请求，366 秒窗口 284/284 请求成功，保存 556 个有效输入，P95 32.46 秒，无重复或限流。

再次探测 32 路的有限窗口为 90 次成功、1 次 504，P95 46.26 秒，13.37 万成功字符/分；24 路完整窗口为 14.26 万字符/分。本次据此回到 24 路持续运行，冷却后再续接。504 后的新门禁阻止了隐式重发，176 个成功输入已保存，2 个新增未知输入隔离；所有未知输入仍保留在原计划分母。不同队列输入不构成受控基准，后续选档继续依据成功吞吐与服务错误，不把机器资源或配置上限当成服务容量。

后续 24 路连续窗口达到 754.6 秒，663/663 请求成功，实际峰值 24，保存 1,307 个新有效输入，P95 33.81 秒，无重复发送、服务错误或本地数据库锁等待。此时固定 621 份中 134 份全部完成，仍缺 19,970 个索引向量行；49 个已知未知结果输入分布在 4 份资料内，继续保留欠账。运行尚未结束，这些数字不表示其后不会限流，也不表示全部资料向量化完成。

## 固定范围执行

正式入口为 `scripts/complete_embeddings.py`。先冻结计划，再使用同一计划续跑；计划包含 `data_dir`、`owner`、`fingerprint` 和 `documents`，每份文档保存 `id`、`version`、`content_hash`、`source_url`、`size`、`storage_path`。预检核对原件字节、正文、分块输入、一级资格及模型标识；不发现或追加新文档，不下载、解析、OCR 或批准法规。

以下路径应替换为本次已冻结的计划、私有工作目录和模型配置文件。首次不加 `--apply` 执行预检；确认预检成功后，在同一命令末尾追加 `--apply` 执行：

```sh
uv run --project backend python scripts/complete_embeddings.py \
  --plan /absolute/private/selection.json \
  --output /absolute/private/embedding-run \
  --models-env /absolute/private/models.env \
  --admission-path /absolute/private/runtime/embedding-admission.sqlite3 \
  --http-workers 64 --document-workers 12 --request-concurrency 2 --batch-size 2 --http-timeout 60
```

`--document-workers` 控制实际后台文档数，允许共享入口上限保持 64、后台按上游承载能力降至 12 份文档（每份 2 请求）。`--max-run-seconds` 可限定观测窗口，到期停止新发并排空，不改变固定清单或删除欠账。

需要无人值守续跑时，在同一正式命令追加 `--supervise --supervisor-window-seconds 300 --supervisor-max-document-workers 12`。监督器仍只运行原冻结计划；单独的监督锁和既有运行锁防止双开。每个窗口排空后保存状态，429 遵守共享冷却和 Retry-After，连续故障延长退避并降低后台文档数；两次有进展且 P95 不超过 40 秒的窗口后，才在明确配置的后台上限内缓慢恢复。配置总入口 64 不随退档改变。监督状态持久化为 `supervisor-state.json`，运行/冷却/证据待补/全部完成分别为 `running`、`cooldown`、`blocked_inputs`、`completed`。

监督进程硬中断后，已启动的子进程继续保存成功结果；重启监督器会先等待既有运行锁，不另开付费任务。子进程也被中断时，下次正常预检从已保存输入继续，并隔离没有确定结果的发送意图。真实进程回归已验证硬杀父进程后的两条输入各只调用一次。未知输入及耗尽后被业务服务标记为结果未知的失败任务保持 `blocked_inputs`，每五分钟重新检查新证据；不会清空失败历史、扩大授权清单或把停止写成完成。只有缺失向量为零且原始资料守卫全部通过才完成。

密钥文件仅后端可读，不提交版本库。运行目录以文件锁避免重复执行；收到 429 后停止新增领取、保存 Retry-After，排空已有请求。启用逐请求持久回调时，已发出的兄弟请求仍在原超时边界内读取并保存有效成功结果；失败不会删除已保存批次。取消和失败后的状态可能是 `stopped`，只有缺失向量为零才是 `complete`。

`issued-requests.jsonl` 在发送前写入并同步请求意图，`requests.jsonl` 按请求 ID 记录终态、输入摘要和结果；重启同时核对两份日志，硬中断后无终态的输入保留为未知结果。`successful-inputs.sqlite3` 保存逐请求校验成功的向量。应用索引提交前再次核对租约、账号、原件、分类和完整输入。已有成功结果不会仅因同批其他请求失败而重新收费请求。对于已发出但结果不明的输入，默认暂缓；`--retry-unresolved` 是显式重试入口，可能再次计费，须保留旧请求记录。正常应用的同输入缓存不能消除两个同时发生的冷请求。

`--retry-unresolved-selection` 可指定绑定账号、模型和冻结计划的精确输入摘要清单。它只放行该清单中启动时仍未决的输入；已有成功缓存优先，新出现的未知结果不会自动加入清单。同一授权清单中某输入恢复后再次返回未知时，预检会从原有 preflight 与请求日志识别已消耗的恢复机会，后续重启也隔离该输入；429 等明确拒绝不消耗这次恢复机会。每个成功 HTTP 批次仍即时保存；每越过 200 个新成功输入另存不可变进度检查点。错误中的 `request_sent`、`request_outcome_unknown` 和 `http_status` 描述最后失败的 HTTP 请求，不能据此推断整个多批调用都未计费。

同库并发入库与模型处理会竞争写事务；[SQLite WAL](https://www.sqlite.org/wal.html#concurrency) 允许读写并行，但同时只有一个写入者。领取和心跳通过共享运行辅助函数，仅对本地已回滚的忙事务最多尝试三次，不把模型调用包进重试。真实 17 秒写锁测试验证了首次 15 秒超时后续期成功、任务尝试数不增、零模型请求。新增资料入库按 40 份分批并记录事务耗时；800 份实测最长 8.50 秒。遇到其他错误停止新领取并排空已发请求，不把运行器退出当作全部处理完毕。

## 备份和迁移

运行中备份应用数据库和独立的 `successful-inputs.sqlite3` 时，都使用 SQLite 在线备份接口，不能只复制主数据库文件而遗漏 WAL。保留不可变计划、原始基线、已有元数据行摘要、请求日志和模型标识，并与原件 CAS、配置及应用数据库的备份清单关联。密钥单独按私有配置交接。

`EMBEDDING_ADMISSION_PATH` 指向运行态目录，放在项目 `.dev/` 或明确配置的独立运行目录，不能放进业务 `data/`。迁移时保留配置规则并为新主机选择同一个新路径，重新创建额度库；不恢复旧机器 PID/等待租约，也不能复制活跃额度文件作为业务备份。先排空旧 API 与后台，再让所有新进程使用同一配置和路径。

应用资料迁移沿用 [存储与备份](STORAGE.md) 的正式流程。计划绑定执行时的数据根和原件路径；迁移后须建立并验证新计划，保留原计划作为审计证据，不覆盖旧计划冒充原地续跑。缓存复用始终核验账号、模型和实际输入，不能跨用户或跨模型直接加载。

2026-10-19 的一次实恢复验证逐行比较了 3,653 份文档、15,763 条向量、584 条关系及其全部索引和元数据；仅原件路径与 17 个暂态租约按设计改变。独立请求检查点备份的 3,868 条向量字节一致，恢复副本实际复用 16 个输入、零模型请求。应用库、请求日志前缀和运行控制文件分别记录快照时间，不能把这些不同时间点的文件视为一个原子快照，或把日志尚无终态的请求当成可以自动重发。

2026-10-19 的共享入口实测中，后台峰值 60 与 4 条真实 RAG 查询叠加达到全局峰值 64；4 条查询耗时 2.07–2.32 秒、全部成功。后台同一轮 100 次请求中 40 次成功、58 次 504、2 次读取超时，保存 80 个有效输入，无重复发送；新 120 个结果未知输入隔离，原文与旧向量守卫均通过。该窗口证明共享额度和查询优先接线生效，未证明供应商可持续承受 60 路后台、每请求 2 段。恢复保持总上限 64，后台降为 12 文档/24 请求并冷却。不同批大小和输入长度不能作为受控吞吐比较。
