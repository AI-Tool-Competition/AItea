# 系统总库迁移到已有应用库

`scripts/migrate_system_corpus.py` 为运维提供离线迁移，底层是 `app.system_corpus_migration`。它固定使用没有登录权限的 `aitea-system-legal-library`，仅向目标插入这一归属的资料、国家、分类及历史、审核历史、关系、处理检查点和检索索引。已有普通用户、会话、业务、事实、消息和配置不会从来源复制，也不覆盖目标数据库。

先停止并等待本任务的采集／识别窗口完成回收，再导出新快照。脚本不会停止任何进程。导出使用只读 SQLite 在线 backup，包含已提交 WAL 内容，不把运行中的数据库主文件直接当作备份；源库和 CAS 不移动、不修改。快照目录为新建私有目录，保存只读数据库、系统归属的不可变 CAS 清单及摘要。CAS 仍保存在源目录，因此成功迁移、核验及保留期结束之前不能删除源工作树或其 `data/`。

```bash
uv run --project backend --locked python scripts/migrate_system_corpus.py export \
  --source-dir <功能工作树>/data --snapshot-dir <新的私有快照目录>

uv run --project backend --locked python scripts/migrate_system_corpus.py migrate \
  --snapshot-dir <快照目录> --target-dir <主工作树>/data \
  --models-env <私有模型配置> --source-stopped
```

`migrate` 默认只读预检，不创建目标目录、不初始化服务或升级结构。`--source-stopped` 表示运维已停止自己的来源 worker；快照和当前源库仍会再次检查处理状态和所有租约字段，源检查点变化后必须重新导出。确认预检无阻塞后，同一命令追加 `--apply`。模型配置仅用于校验向量指纹，不调用模型、不输出密钥。配置不匹配时整次拒绝，不把历史向量当作当前模型向量。

执行首先为目标做在线 SQLite 备份，然后通过已有 `Service` 完成结构升级，随后按快照协议以单事务或有界批次迁移系统资料。备份默认位于目标 `data/migration-backups/<唯一目录>/tea.sqlite3`，也可显式提供新的 `--backup-dir`。结构升级与资料复制分开，当前资料事务失败不会悄悄撤销已经提交的结构升级或此前已提交的资料批次；备份保留升级前的普通用户、会话和业务。错误发生后先停止目标所属服务、保留备份及新 CAS，核对报告后使用相同备份点恢复数据库，不覆盖运行中的 WAL 库。

所有系统 CAS 原件、整页图片和证明先验证 SHA，再在写事务外发布到目标同一归属。迁移保持文档 ID、family、版本、manifest 字符串、页级 OCR 复用证明、registry 和映射文件原始字节；仅 `documents.storage_path` 的绝对目录前缀改为目标数据目录。manifest 中可执行的 CAS 路径必须已经是系统归属的相对路径，禁止留下指向旧工作树的绝对地址。内部检索 chunk rowid 可重映射，向量原 float32 BLOB 不再次归一化；其输入、维度、有限值及单位长度必须通过已有校验。

法定二级资料继续保留正文且不产生向量，普通关联附件继续只保存原件。审核、日期、疑点、分类与历史不会被迁移批准。失败和待核页保留，真正待处理任务继续排队，活动 token 和租约不进入目标。完全相同的重复请求可跳过原件版本；目标已有修改、活动处理、文档／关系标识冲突、模型维度冲突或审核人缺失时拒绝覆盖。

来源快照可能包含源库自身的其他私有表，但只在私有快照目录供运维保留；迁移查询限定固定系统归属，其他账号及业务行不进入目标。所有网络调用均被 CLI 禁止。原件、文本和真实向量迁移成功仍不等于法律审核完成，正式 RAG 继续遵循系统库审核、生效期、完整性和版本门禁。

## 大库分批迁移与中断续接

新导出在超过 40 份资料，或资料正文、处理历史、分块和向量的估算原始数据超过 64 MiB 时自动使用 `system-corpus-migration-v2`。小库仍保留 v1 的单事务行为。旧 v1 大快照需要重新导出，避免通过兼容入口恢复过大的写事务。

v2 上限为 50,000 份资料、每张迁移表 5,000,000 行、迁移行数据合计 64 GiB、500,000 个 CAS 文件及合计 512 GiB CAS；实际磁盘空间仍须另行预留。单份 manifest 最多 40 MiB，单份资料及其直接派生行合计最多 64 MiB；超界会在写入前拒绝。这个容量范围包含 30,000 份资料，但也受上述字节与行数边界限制，不表示所有大小的文件组合均可容纳。

快照摘要逐行计算，先在 SQLite 中检查行体积，再读取正文和向量。内存中保留有上限的标识、文件清单和摘要，以及当前批次的正文；跨批原件、OCR 复用和向量复用只读查询同一个冻结快照，最多缓存两份引用文档。每次事务最多 40 份资料及 64 MiB 估算原始数据。Python 对象、解析后的 JSON 和校验临时值会占用额外内存，该字节预算不是进程 RSS 上限。

写事务设有 10 秒的执行预算，超过预算的批次回滚并拆分重试；单份仍超出时停止并保留进度。SQLite 语句进度回调和提交前检查用于执行阶段，不能限制 `COMMIT` 的磁盘同步时间。报告的 `maximum_transaction_seconds` 实测包含提交；`transaction_execution_budget_seconds` 是执行预算，`commit_duration_hard_limit=false` 明确没有提交耗时的硬保证。批次外复制 CAS、校验源文件和读回全量摘要，不持有全库写锁。

操作时同时暂停来源和目标的采集、解析、向量 worker，并等待各自租约结束；普通用户数据不作为迁移对象。脚本不停止进程，不重置他人的队列。源库提交版本或数据库身份在迁移期间变化会拒绝继续，目标已处理或修改的检查点也不会被覆盖。与小库一样，带有系统账号恢复账本的 schema19 来源必须走完整备份恢复，不能用系统子集迁移丢弃恢复历史。

资料依主文件、附件顺序分批提交，关系在两端均已写入后逐条提交。每批同时保存正文、历史、处理任务、索引和原向量 BLOB，失败只回滚当前批次。迁移备份目录的 `migration-progress.json` 以原子替换和 fsync 记录固定快照摘要、已提交数量与实际耗时。它用于定位进度；重启时仍从固定快照核验目标的真实行，不盲信游标。

中断后保留最初的目标备份和已发布 CAS，使用相同快照、目标目录、模型配置及 `--source-stopped --apply` 重新执行。已完整提交的资料逐项核验后跳过，未完成批次继续，关系阶段中断也能重放。每次应用保留一个新的目标数据库备份，不覆盖最初的恢复点。已提交的目标资料发生变化、出现其他系统资料、私有文档 ID 或关系 ID 冲突时拒绝覆盖，不能通过清空目标库来绕过。

两种迁移路径均支持正式的 `same-owner-original-embedding-reuse-v1` 和 `same-owner-input-embedding-reuse-v1` 证明。后者逐条核对来源原件版本、相同输入、模型指纹、维度及两端向量摘要；不按提供方重新计算，不把来源定位或审核状态复制为目标的法律批准。历史计数与请求记录原样保留，不作为成功向量的替代证据。
